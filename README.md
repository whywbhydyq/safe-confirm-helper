# Safe Confirm Helper 插件介绍与使用说明

## 1. 插件是什么

Safe Confirm Helper 是一个运行在 ChatGPT 网页端的长任务监督插件。

它的目标不是替用户验证所有业务结果，也不是接管 GitHub、Vercel、本地文件或外部测试环境。它真正做的是：当用户让 ChatGPT 执行较长、较复杂的任务时，插件强制 AI 在停止前进行自检，并且只有输出合格的 `<SCH_FINAL>` 终止块后，插件才停止自动继续。

一句话概括：

```text
用户正常给 ChatGPT 下任务，插件负责防止 AI 只说“任务完成”就提前停下。
```

## 2. 核心使用流程

当前版本采用按钮开启监督，不再依赖插件自动判断“这是不是长任务”。

用户流程是：

```text
1. 安装插件
2. 打开 ChatGPT
3. 点击插件弹窗里的“开启持续监督”
4. 像平常一样输入真实任务
5. 插件在发送任务时自动追加监督协议
6. ChatGPT 执行任务
7. 如果没有合格 SCH_FINAL，插件自动继续或触发审计
8. 如果出现合格 SCH_FINAL，插件自动停止
```

也就是说，插件不应该在用户刚点击按钮时立刻发送“最终自检”。点击按钮只表示“进入待命状态”，真正的监督从用户发送真实任务后才开始。

## 3. 它解决什么问题

ChatGPT 做长任务时常见问题包括：

- 执行到一半就总结。
- 没有覆盖全部要求，却说“任务已完成”。
- 忘记最初的约束和目标。
- 没有说明哪些内容没有验证。
- 没有区分阻塞风险和非阻塞风险。
- 用户需要反复手动输入“继续”。

Safe Confirm Helper 通过一套轻量停机协议，把“能不能停”的条件从自然语言改成结构化门控。

旧逻辑的问题：

```text
只要 AI 回复里出现“任务已完成”，插件就可能停止。
```

新逻辑：

```text
只有 AI 输出合格的 <SCH_FINAL> 块，插件才停止。
```

## 4. SCH_FINAL 停止协议

合格的最终块格式如下：

```text
<SCH_FINAL>
status: done
covered: ...
proof: ...
unverified: none
risks: none
verdict: ready_to_stop
</SCH_FINAL>
```

字段含义：

- `status`: 必须是 `done`。
- `covered`: AI 声明已经覆盖的原始需求。
- `proof`: AI 给出的完成证据或检查依据。
- `unverified`: 未验证事项；没有时必须写 `none`。
- `risks`: 残余风险；没有时必须写 `none`。
- `verdict`: 必须是 `ready_to_stop`。

插件停止的必要条件：

- 存在 `<SCH_FINAL>...</SCH_FINAL>`。
- `status` 是 `done`。
- `unverified` 是 `none` 或等价的空表达。
- `risks` 是 `none`，且不包含阻塞风险词。
- `verdict` 是 `ready_to_stop`。

插件不会因为这些内容停止：

- “任务已完成”
- “已完成”
- “done”
- “finished”
- 不完整的 Final 块
- `unverified` 非空
- `risks` 中存在阻塞风险
- `verdict` 不是 `ready_to_stop`

## 5. 当前状态模型

插件内部任务状态可以理解为四类：

```text
idle
未开启监督。

armed
用户已经点击“开启持续监督”，插件正在等待用户发送真实任务。

supervising / continuing / auditing
真实任务已经发送，监督协议已经注入，插件正在监督 AI 输出。

unblocking
AI 声明存在未完成、未验证、失败或阻塞项，插件正在推动它换方案继续。

paused_blocked
AI 连续声明必须用户外部操作才能继续，插件暂停等待用户处理。

stopped_valid_final
已经检测到合格 SCH_FINAL，插件停止自动继续。
```

其中最关键的是 `armed` 状态。

在 `armed` 状态下：

- 插件不会发送最终自检提示。
- 插件不会自动继续。
- 插件不会因为当前页面旧回复里没有 Final 块而触发审计。
- 插件只等待用户输入真实任务。

用户发送真实任务后，插件会把监督协议追加到任务末尾，然后进入真正监督状态。

## 6. 插件会自动做什么

### 6.1 追加监督协议

用户点击“开启持续监督”后，下一次发送真实任务时，插件会在任务后追加类似协议：

```text
[SafeConfirm Supervision]
本任务按长任务处理。不要用一句“任务已完成”结束。
执行时优先完成原始需求；停止前必须自检是否有遗漏、未验证项和阻塞风险。
如果仍有未完成、未验证项或阻塞风险，继续执行。
如果确认可以结束，只输出 SCH_FINAL 块。
```

插件不会在按钮点击瞬间单独发送这个协议。它会跟用户的真实任务一起发送。

### 6.2 自动继续

如果 AI 停止后没有合格 `<SCH_FINAL>`，插件会发送短继续提示，要求 AI 继续原始任务。

默认继续方向是：

```text
继续执行原始任务，从当前进度后的下一个具体步骤开始。优先处理未完成、未验证或有阻塞风险的部分。
```

### 6.3 解阻继续

如果 AI 明确说任务未完成、未验证、工具失败、权限不足、无法部署、不能输出 SCH_FINAL，插件不应该继续要求它做停机前自检。

这类情况会进入 `unblocking`，发送通用解阻提示：

```text
当前任务尚未完成。不要做停机前自检，不要输出 SCH_FINAL。
请把未完成项、未验证项或阻塞点转化为下一步行动：
能继续执行就继续；能换工具或换路径就换方案；能降级交付就先完成替代方案。
只有确实必须用户外部操作且无法继续推进时，才暂停并说明需要用户做什么。
```

这一步的目标是让 AI 继续解决问题，而不是反复证明自己没有完成。

### 6.4 自动审计

当 AI 明确表达完成、输出过 Final 块、页面检测到 Final，或达到审计间隔时，插件会触发短审计提示，让 AI 先做最终自检。

审计不是为了替用户判断业务结果是否真的正确，而是强制 AI 把覆盖项、证据、未验证项和风险说清楚。

注意：普通风险词本身不应该直接触发最终审计。比如 AI 说“当前还有阻塞”“未验证”“不应视为 ready_to_stop”时，正确动作通常是继续执行或修复，而不是立刻塞入停机自检。

### 6.5 分阶段提示词

插件按阶段使用不同提示词，避免一开始就触发最终自检：

```text
开启监督
只进入 armed 待命状态，不向 ChatGPT 发送提示。

发送真实任务
把短监督协议追加到用户任务后面，要求 AI 先执行原始需求。

普通继续
要求 AI 从当前进度后的下一个具体步骤继续做，不要复述计划或阶段性总结。

解阻继续
当 AI 承认未完成、未验证或遇到失败时，要求它换方案继续推进。

最终审计
只在准备停机、出现 Final、明确完成意图或达到审计间隔时触发；如果发现遗漏、未验证项或阻塞风险，要求 AI 继续执行或修复。

合格停止
只接受完整 <SCH_FINAL> 块。
```

### 6.6 自动确认按钮

插件保留安全确认辅助能力，可识别 ChatGPT 页面上的确认类按钮，例如：

```text
确认 / 允许 / 继续 / 批准
Confirm / Allow / Continue / Approve / Accept
```

自动点击只应发生在可见、安全、匹配的确认按钮上。

### 6.7 保持底部

自动继续开启时，插件可以帮助页面保持在最新回复附近，方便观察长任务进度。

保持底部不应该独立抢滚。当前规则是：只有自动继续开启时，保持底部才生效；自动继续关闭时，保持底部也应该停止。

## 7. 插件不会做什么

Safe Confirm Helper 不是万能验证器。

它不会：

- 验证 AI 的 proof 是否 100% 真实。
- 自动跑本地测试。
- 自动访问 GitHub、Vercel 或生产环境。
- 自动修改仓库、提交代码或部署。
- 要求用户写 JSON、YAML、assertions。
- 替代 IDE Agent 或完整自动化平台。

插件的边界是：

```text
AI 负责执行任务和自检。
插件负责强制 AI 不能跳过自检流程。
```

## 8. 安装方式

1. 打开 Chrome 扩展管理页：

```text
chrome://extensions/
```

2. 打开右上角“开发者模式”。
3. 点击“加载已解压的扩展程序”。
4. 选择本项目目录：

```text
safe-confirm-helper
```

5. 打开或刷新 ChatGPT 页面：

```text
https://chatgpt.com/
```

## 9. 使用方式

推荐流程：

1. 打开 ChatGPT。
2. 点击浏览器扩展图标，打开 Safe Confirm Helper 弹窗。
3. 点击“开启持续监督”。
4. 回到 ChatGPT 输入框，输入真实任务。
5. 正常发送。
6. 插件会自动追加监督协议。
7. 等待 ChatGPT 执行。
8. 插件会持续继续或审计，直到出现合格 `<SCH_FINAL>`。

弹窗状态说明：

- “监督已开启”：已经点击按钮，正在等待你发送任务。
- “正在监督当前对话”：任务已经发出，插件正在监督。
- “最终自检未通过”：AI 输出过 Final，但字段或风险条件不合格。
- “最终自检通过”：检测到合格 Final，插件停止继续。
- “已暂停”：达到最大继续次数、发送失败、找不到输入框或用户手动暂停。

## 10. 常见问题

### 为什么点击按钮后没有马上发送提示？

这是正确行为。

按钮只是开启监督待命状态。插件会等你输入真实任务，并把监督协议追加到你的任务后面一起发送。

### 为什么以前一打开就触发“最终自检”？

那是旧状态机问题。

旧逻辑把按钮启动直接当成“任务正在监督且缺少 Final”，所以插件会马上审计。正确逻辑应该是：

```text
按钮点击 -> armed
用户发任务 -> supervising
AI 缺 Final -> continue/audit
AI 有合格 Final -> stop
```

### 断网刷新后为什么弹窗显示不可用？

如果 ChatGPT 页面本身没有加载完成，插件的 content script 也无法运行，弹窗就无法连接页面。

这不一定代表任务数据丢失。当前任务状态会尽量保存在 `chrome.storage.local`，但只有 ChatGPT 页面重新加载并注入脚本后，插件才能恢复和显示状态。

### 普通聊天会被插件干扰吗？

在当前按钮模式下，只有你点击“开启持续监督”后，插件才会接管下一条真实任务。

如果不想监督当前聊天，可以点击“重置当前任务”或关闭自动继续。

### AI 输出了 Final，为什么还在继续？

可能原因：

- Final 缺少字段。
- `unverified` 不是 `none`。
- `risks` 包含阻塞风险或风险词。
- `verdict` 不是 `ready_to_stop`。
- Final 块格式无法被解析。

插件会把这些情况当成“不能停止”，继续推动 AI 修复或说明。

## 11. 已踩过的坑

这些问题都是开发过程中实际踩过的坑，理解它们有助于维护这个插件。

### 11.1 不要把“点击开启监督”当成“立刻开始审计”

最早的错误是：用户点击按钮后，插件立即把任务状态设成 `supervising`，并把 `lastGateReason` 设为 `missing_final`。

这会导致插件刚开启就认为“AI 缺少最终自检”，于是直接发送审计提示。正确做法是引入 `armed` 状态：

```text
点击按钮 -> armed
用户发送真实任务 -> promptInjected: true
AI 停止且回复稳定 -> maybeContinue
合格 SCH_FINAL -> stopped_valid_final
```

`armed` 状态只表示插件待命，不能自动继续、不能审计、不能根据页面旧回复判断任务状态。

### 11.2 不要只看最后一条文本就立刻继续

ChatGPT 页面从后台切回前台时，DOM 可能已经有最后一条 assistant 文本，但这不代表对话真的稳定结束。

如果此时立即判断，就会出现任务还没完全跑完、输入框却已经被填入继续或审计提示的问题。

当前规则是：

```text
页面必须可见
最后一条 assistant 文本必须连续稳定一段时间
不能处于 generating / thinking / running 状态
输入框不能有用户草稿
```

只有同时满足这些条件，插件才允许自动继续或审计。

### 11.3 风险词不等于停机审计

曾经的错误逻辑是：只要 AI 回复里出现“未验证、阻塞、无法确认、可能、ready_to_stop”等词，就触发最终审计。

这会误伤真实执行过程。比如 AI 说：

```text
当前结论：仓库已上传成功一次，但原始优化任务未完成，不应视为 ready_to_stop。
```

这句话的含义其实是“还没完成，应该继续执行”，不是“准备停机”。所以风险词只能作为继续执行的依据，不能单独作为最终审计依据。

更稳的触发条件是：

```text
出现完整或不完整 Final 块
AI 明确表达任务完成
页面增强脚本检测到 Final
达到审计间隔
```

### 11.4 旧提示词会污染新逻辑

用户浏览器里可能已经保存了旧版继续提示，例如：

```text
继续执行最初的任务。不要总结，不要停下，直到最初任务全部完成。完成后请只回复：任务已完成
```

如果不迁移这个旧配置，即使代码已经升级，插件仍然会把旧提示写进输入框，看起来像新逻辑没有生效。

所以设置加载时要识别旧默认提示，并自动迁移到当前版本的默认继续提示。输入框里如果残留插件自己的旧草稿，也应该识别为插件草稿，而不是当成用户输入。

### 11.5 自动继续和保持底部要绑定

保持底部看似是独立功能，但实际体验上它会抢滚动。用户只想手动看页面时，如果保持底部独立开启，会让页面不断贴到底部。

当前规则是：

```text
autoContinue 关闭 -> keepAtBottom 不生效
autoContinue 开启且 keepAtBottom 开启 -> 才自动贴近最新回复
```

这样可以避免普通浏览和手动检查时被强行拖到底部。

### 11.6 自动确认不能只依赖 dialog

ChatGPT 的确认卡片不一定总是标准 `dialog`。例如 GitHub 工具确认可能以内联卡片形式出现，按钮周围有“拒绝/确认”两个操作，但 DOM 不一定命中弹窗选择器。

如果只扫描 dialog，插件会高亮候选按钮但不自动点击。

更稳的策略是：

```text
标准 dialog 内的确认按钮可以自动点
非 dialog 场景下，只在小按钮组里同时存在“拒绝/取消”和“确认/允许/批准”时，才认为是安全确认卡
```

这比全页面遇到“确认”就点更安全。

### 11.7 写入输入框不代表已经发送

另一个实际问题是：插件把继续提示写进输入框后，发送按钮可能还没启用，或者 ChatGPT 改了发送按钮的 selector，于是提示卡在输入框里。

因此发送逻辑需要：

```text
支持多个发送按钮 selector
重试等待发送按钮启用
必要时用 Enter 作为兜底
Enter 兜底后仍要检查输入框是否变化，不能按了键就假设发送成功
如果输入框里已经是插件自己的草稿，允许继续尝试发送
如果输入框里是用户草稿，不覆盖
```

### 11.8 文案优化不能代替状态机

提示词可以降低误判，但不能替代代码状态机。

比如“不要一开始就做最终自检”写得再清楚，如果插件在按钮点击后立即发送审计提示，AI 仍然会被带偏。真正可靠的规则必须落在代码里：

```text
未 promptInjected -> 不继续、不审计
回复未稳定 -> 不继续、不审计
页面不可见 -> 不继续、不审计
风险词 -> 默认继续，不默认审计
```

## 12. 技术结构

主要文件：

```text
manifest.json
Chrome 扩展配置，声明权限、图标、popup 和 content scripts。

content.js
核心页面脚本。负责任务状态、监督协议注入、SCH_FINAL 解析、停止门控、自动继续、自动确认、状态持久化。

popup.html / popup.css / popup.js
插件弹窗界面。负责显示连接状态、任务状态、继续次数、Final 状态和设置项。

sch-final-enhancements.js
页面增强脚本。负责折叠 Final 块、识别页面风险信号，并把信号传给 content.js。
```

关键状态字段：

```js
{
  active: true,
  status: "armed",
  promptInjected: false,
  lastFinal: null,
  lastGateReason: "",
  stopReason: ""
}
```

关键判断：

```text
没有 promptInjected 时，不允许自动继续或审计。
只有 promptInjected 后，插件才读取最后一条 assistant 回复并判断 Final。
```

## 13. 当前产品原则

Safe Confirm Helper 的设计原则是：

- 用户零额外配置。
- 用户点击按钮即可开启监督。
- 不再自动猜测任务是否长任务。
- 不用“任务已完成”作为停止条件。
- 只接受合格 `<SCH_FINAL>` 作为停止条件。
- 插件不做万能业务验证。
- 尽量减少对普通对话的干扰。

最重要的一条：

```text
点击按钮不是让插件马上审计当前页面，而是让插件等待用户的下一条真实任务，并监督它直到合格停止。
```
